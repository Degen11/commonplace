# migration.sql cannot be re-applied to an existing database, so later appended security statements only land by hand

Confirmed by detect-security: Evidence resolves: every statement in supabase/migration.sql is guarded (IF NOT EXISTS / OR REPLACE / DROP IF EXISTS) except CREATE TRIGGER at line 35, so a re-run against an existing DB errors and the multi-statement run rolls back the appended RLS enable (line 101) and policy drop (line 118). No CI job touches the schema (.github/workflows/ci.yml has no supabase/postgres step), no documented reset path, and api/sync.js:51 and :103 keep collections-column fallbacks for exactly this drift. Fresh-from-empty replay works, so this is the re-apply variant of Case 4, not a squashed-baseline trap.
