# identifyBatch discards the server error message, so the AI daily-cap notice shows as a generic 'wait a moment' rate limit

Confirmed by detect-code: useProcessing.js:130 throws only 'API returned <status>' with no body read and no .status. apiErrors.js:9 maps any 429 to 'Wait a moment and try again'. api/identify.js:134-136 returns the 429 AI_DAILY_LIMIT 'try again tomorrow' message, which is lost. The handleApiBatch retry (useProcessing.js:260ff) re-calls on that 429. apiRequest (api.js:72) and autoGroup (:516) do read the body. Divergence verified, no documented reason.

Evidence:
- src/hooks/useProcessing.js:130
- src/hooks/useProcessing.js:516
- src/utils/api.js:72
- src/utils/apiErrors.js:9
- api/identify.js:136
- commit db4af86 Security hardening: AI spend cap, per-endpoint rate limits, SSRF, cache poisoning, sync ID

Kind: duplication.

How to fix: In identifyBatch, read the JSON body on a non-OK response and throw its error message with .status attached, as apiRequest does, and let describeApiError prefer a server-supplied message.
